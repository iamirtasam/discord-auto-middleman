# discord-auto-middleman

A self-hosted Discord bot that acts as an **automated Litecoin (LTC) middleman / escrow agent**. Two users open a private trade thread, the sender deposits LTC into a **one-time escrow address** generated by [Tatum](https://tatum.io), the bot watches the blockchain through [BlockCypher](https://www.blockcypher.com/), and once the deposit is confirmed the bot releases the funds (or refunds them) with **no human middleman** — 24/7.

> **Status:** production use · UI fully converted to **Discord Components V2** (`discord.js ^14.28.0`, zero `EmbedBuilder` left in shipped code) · auto-uploaded application emojis · JSON + MongoDB persistence.

### What makes it "auto"

01. **PANEL →** user clicks *Start Auto Middleman* → bot opens a **private thread** in the configured support channel.
02. **PARTIES →** the thread owner names the counterparty; both pick Sender/Receiver and confirm (with reset/cancel).
03. **DEAL →** currency (EUR/USD) is chosen and double-confirmed; the sender types the fiat **deal amount**.
04. **ADDR →** the bot converts fiat → LTC (CryptoCompare), adds the network-fee buffer, and derives a **one-time deposit address + private key pair from an xpub/mnemonic index** (Tatum).
05. **INVOICE →** a CV2 payment card with **Copy** address, **Show QR** buttons and a blurred `||@sender||` pin.
06. **WATCH →** a polling loop on BlockCypher detects incoming (even unconfirmed) transactions.
07. **RECONCILE →** if the received LTC is less than agreed, the bot offers *Send More* (fresh remaining-amount invoice) or *Continue* (proceed with what landed).
08. **WAIT →** the bot tracks the tx to **≥ 1 confirmation** on the chain before anything else happens.
09. **WALLET →** the sender-only **Release / Cancel** wallet card appears.
10. **PAYOUT →** *Release*: the receiver types their LTC address, confirms it, and the bot sweeps the escrow via Tatum — then auto-posts payment + transcript webhook logs, assigns a `client` role, and self-destructs the thread after 24h. *Cancel*: same mechanics in reverse — refund back to the sender.

### Boot sequence

```
node index.js
 ├── Client({ intents, partials, shards: "auto" })
 ├── handlers/command.js  → client.commands Collection
 ├── handlers/event.js    → client.on(...) for every events/*.js
 ├── process traps: unhandledRejection / uncaughtException / uncaughtExceptionMonitor / shardError
 └── login(config.token)
      │ (ready — once)
      ├── database/mongodb.js      → mongoose.connect(mongoURL)
      ├── functions/emojiSync      → sync application emojis (see Emoji pipeline)
      ├── REST.put(applicationCommands) → **global** slash registration (not guild-scoped)
      └── presence: "Watching irtasam", status dnd
```

- `handlers/command.js` filters `slashcommands/*.js`; a leftover `balance1.js.old` file is therefore **not** loaded.
- `events/interactionCreate.js` re-reads `slashcommands/` **at each chat-input interaction** (files are hit fresh, so hot-editing a command takes effect without restart).
- `events/ready.js` registers commands via `Routes.applicationCommands(client.user.id)` — **global** registration despite `guildID` being in config.

### The two stars

- **`functions/trade.js` — class `Trade`.** One instance per private thread. Owns the whole lifecycle: role selection, currency, both amount confirmations, address/key generation, deposit polling, underpayment recovery, confirmation tracking, release/cancel, payout, webhook logging, thread teardown. Header of the file is the constructor with ~20 lifecycle fields (see [Trade state machine](#trade-state-machine)).
- **`functions/ui.js` — the design system.** Every visible message in the project is built here; there is **no `EmbedBuilder` and no `content:` string** anywhere in shipped code (outside ephemeral one-liners and raw notes) — see [The Components V2 UI design system](#the-components-v2-ui-design-system).

### Stage 0 — Panels

`/panels` (admin) → `functions/createPanel.js` builds, in one go:

1. The **flagship CV2 panel** (bot-avatar section, headings, features, safety copy, fee explainer, one `Start Auto Middleman` button → customId `create_new_deal`) in the configured panel channel.
2. A **Status card** (`The AutoMM is currently operational ✅`) in the same channel.
3. The **Admin Controls** card (`toggle_automm` / `close_threads` buttons) in the admin control channel.

The (guildId → channelId, messageId) triple is stored in MongoDB (`database/panel.js`), so `/panels` rebuilds cleanly: it deletes the old message, drops the doc, and re-creates everything.

Channel IDs used by the admin controls are **hard-coded constants** at the top of `createPanel.js` (`panel_channel_id`, `control_channel_id`) — see [Known quirks](#known-quirks--technical-debt).

### Stage 1 — Thread creation

`interactionCreate` handles `create_new_deal`:

1. Fetches `config.thread_channel`; creates a **private thread** inside it.
2. Posts a CV2 **confirm card**: `Are you sure you want to open a trade?` with `openTrade` / `cancelTrade` buttons (3-minute window; no response ⇒ thread deleted).
3. On `openTrade` → `new Trade(buttonInteraction, thread)` and `queueMicrotask(() => trade.start(msg))`.
4. The original command reply gets edited to `Created Trade → <#thread.id>`.

If the AutoMM is **disabled** via the admin toggle, the panel button carries its disabled state across the edit (the button-builder's `.disabled` flag is flipped in place, so the panel needs no re-render).

### Stage 2 — Roles

`Trade.start()` posts the **Start/New Trade** card (`startCard`) asking for the counterparty's ID or `@mention`, then `askUserid()` opens a message collector:

- Input is validated by `client.users.fetch` — malformed/unknown IDs retry (`handleMaxRetries`, 5 attempts total).
- On success the thread is renamed `Trade with @owner and @user`, the counterparty is invited, and the stripped-down **welcome card** (`xembed`) posts with a `||@owner||&&||@counterparty||` spoiler ping and the trade rules.
- `initRoleSel()` builds the **Verify Trade Details** panel (`roleCard()` — shared CV2 builder reused for every edit of this message) with `sender`-style role buttons.
- `startRoleCol` collects role picks; picking a role twice flips ownership (`handleRoleSelection`), occupied roles prompt `The X role is already occupied…`.
- Both parties press **Confirm** (`confirmRolesx`) on the confirmation strip (**Confirm / Reset / Cancel**): the reset path deletes the role panel and re-inits it, the cancel path closes the thread. When both roles are confirmed the role panel is edited to its **buttonless** form and `chooseCurrency()` starts.

### Stage 3 — Currency & amount

`chooseCurrency` (`currencyCard()` factory):

1. **EUR / USD** buttons — first pick is locked in; both users must confirm (`.confirm` on the **Confirm your selection** card). Each confirmation posts `@user confirmed the currency.`.
2. Buttons are then re-rendered disabled (classic `ActionRow` edit trail on the currency message).
3. `colDealAmt` posts the **Enter Deal Amount** card and waits for the *sender* to type an amount (regex `\d+(\.\d+)?`, `$` stripped, 30-minute window).
4. `confirmDealAmount` — the amount is stated back on a **Confirm Deal Details** card (`dealCard()`): both users confirm (`confirmDeal` / `cancelDeal` / `resetDeal`). Unresolved ⇒ `Deal amount not fully confirmed. Trade process cancelled.`

### Stage 4 — Escrow address (`ready()`)

Fans out three Tatum operations in one `Promise.all`:

| Promise         | Tatum SDK call                                                   | Result                 |
|-----------------|------------------------------------------------------------------|------------------------|
| Fiat → LTC      | *(CryptoCompare, not Tatum)* `UsdToLtc(dealAmount)`              | LTC gross for the deal |
| Deposit address | `ltcGenerateAddress({ xpub, index })` → `this.addy`              | one-time LTC address   |
| Private key     | `ltcGenerateAddressPrivateKey({ index, mnemonic })` → `this.key` | matching sweep key     |

- `index` is a **per-trade unique number** (`generateUniqueNumber`) — the HD derivation index.
- `ltc_to_receive = UsdToLtc(dealAmount) + this.fee` where `fee = 0.000013` LTC (constructor constant; documented quirk — see fees).
- Every step retries 3× with 5 s spacing; a total failure throws and the flow aborts (thread guidance: `/help`).

### Stage 5 — Invoice (`sendLTCaddy`)

The **Payment Invoice** CV2 card posts *into the thread*, containing:

- a blurred `||<@sender>||` top node — the only "ping" is opt-in (`allowPing: true`, `allowedMentions` respects it),
- bold-procedural instructions (*COPY and PASTE the EXACT AMOUNT*),
- `Address`, `LTC` (exact amount with fee), `Currency` fields,
- action row: **Paste** (`paste|{addy}|{ltc_to_receive}` → ephemeral reply with address, then amount) and **Show QR** (`qr|…`).

QR flow (`interactionCreate`): builds `litecoin:{addy}?amount={amount}` URI → 512×512 PNG via the `qrcode` package → written to `{addy}.png`, attached, rendered **inside a media gallery** with `attachment://{addy}.png`, and **deleted from disk after 5 s**.

`Trade.waitForTransaction()` now starts.

### Stage 6 — Deposit detection

`waitForTransaction` loops:

1. `checkTransactions()` → `GET https://api.blockcypher.com/v1/ltc/main/addrs/{this.addy}/` with a **rotating API key** (`getNextApiKey` picks a random token from `config.apiToken[]`, never repeating the previous one) and 3 attempts with exponential backoff (2^n seconds).
2. Detection condition (either): `total_received + unconfirmed_balance` grew beyond `receivedAmount`, **or** a new `unconfirmed_txrefs` entry appeared (`length ≥ sendMoreCounter`).
3. On detection: `receivedAmount` (sar 8-dec LTC) and `usd` (via `ltcToUsd` → CryptoCompare, stored with `current_rate`) are finalised and persisted (`this.progress = "Money Received …"`).

**Not enough arrived?** → `incuff()` posts the **Amount Mismatch** card (blurred `||<@sender><@receiver>||` pin, `Send More` / `Continue` row):

- **`addmore` →** increments `sendMoreCounter` and re-runs `sendMore()` — a fresh **Updated Payment Invoice** card for the remaining LTC (`Remaining Amount` backtick field) reusing the same `this.msg` / `this.bb` card handles for the edit trail.
- **`continuex` →** posts *Deal Proceeds with Received Amount* (edit trail) + a **Trade Notification** card for the non-sender, then proceeds onward with whatever arrived.

### Stage 7 — Confirmations (`fetchTaxID`)

- Builds the **Transaction Detected** card *once* with the values captured at loop entry (same frozen snapshot behaviour as the old embed flow) and drives `this.bb` (edit if it exists, else send) through the loop.
- Poll cadence: `config.timeout` ms **plus 1.5–2.5 s random jitter**, inside a `while (result.confirmations === 0)` loop.
- The loop exits at `confirmations ≥ 1` → `continueDeal()`. **Nothing detected at all?** The loop's no-transaction branch posts the **Transaction Not Detected** card (sender pinned, `Re-scan` / `cancel` row) and waits **up to 80 minutes** on that card:
- `rescan` → restarts the detection loop, trail rewrites the card into *Requested Rescan*.
- `close_trade` → if anything was ever received, `handleCancel` (refund path); otherwise the thread is locked, renamed `Closed!` and deleted after 2 s.
- Decision timeout (`InteractionCollectorError`) → same lock-rename-delete teardown.

### Stage 8 — Wallet actions (`continueDeal`)

The **Amount Received** card (mentions re-ping via `allowPing`) shows amount, address and fiat value, with (**Release** / **Cancel**) buttons *sender only*:

- `releasex` → `handleRelease(interaction)` — the release flow below (604800000 ms = 7-day interaction window).
- `cancel` → `handleCancel(interaction)` — confirm strip (`confirmCancel` / `denyCancel`):

  - **Both parties** must confirm (`Confirmed Trade Cancellation` notes); the thread owner's card is then edited into **Trade Canceled** — `||<@sender>||` pin, *"Your funds will be refunded…"*.
  - The sender types their LTC address; confirm card (**Confirm LTC Address**, custom accent `0x303238`, `Yes, Correct Address` / `Reset`) → **refund sweep** via the same `sendLTC` machinery.
- Unauthorised clickers (receiver, randoms) get `You are not authorized to …` ephemeral notices.

### Stage 9 — Payout (`handleRelease → sendLTC`)

1. **Confirm Payment Release** card (`Yes!` / `No!`, `confirmRelease` / `cancelRelease`).
2. The *receiver* messages their LTC address in the thread; a message collector validates against the LTC regex `^(L|M)[a-km-zA-HJ-NP-Z1-9]{26,33}$|^ltc1[a-z0-9]{39,59}$` (decoded Bech21-style prefix acceptance).
3. Sender confirms the address (**Confirm LTC Address** card trail, same two-button row, mirror of the cancel path).
4. `sendLTC(receiverAddress)`:

   - `checkbalance(escrowAddr)` → `total_received + unconfirmed_balance` (satoshis → LTC),
   - computes the sweep amount `finalBalance = balance × 0.50 − fee` (see [Known quirks](#known-quirks--technical-debt) — payout math),
   - `sdk.ltcTransferBlockchain({ fromAddress:[{address: escrowAddr, privateKey: this.key}], fee, changeAddress: receiverAddress, to:[{ address: receiverAddress, value: finalBalance }] })`,
   - posts a **Funds Released** card (txid linked to BlockCypher explorer, live `<t:…:F>` timestamp).
5. **Auto-completion chores** (in order): payment webhook card (`logHandler('logs')`), transcript webhook card with inline HTML file (`logHandler('transcript')`), `client_role` assignment to both parties (if configured), **Transcript Manager** card in the thread, an `Anything Else?` note after 6 s, and — after **24 h** — the thread deletes itself.

Total payout latency: BlockCypher confirm + Tatum transfer + webhook round-trips. `this.data = { sender, receiver, amount, txid, channel }` is the payload both webhooks receive.

<p align="center">
  <img src="assets/readme/state-machine.svg" alt="State machine strip: Idle, Thread, Roles, Currency, Amount, Invoice, Detecting, Confirmed, Wallet, Released or Refunded, Closed, with progress strings" width="100%">

Every `Trade` instance is a set of ~20 mutable fields; the per-thread escrow state is what survives a restart:

| Field                                                                                                                                                      | Meaning                                      | Persisted?          |
|------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------|---------------------|
| `interaction.id / thread.id`                                                                                                                               | identity — state key and restart-match key   | Yes                 |
| `sender`, `receiver`                                                                                                                                       | party IDs                                    | Yes                 |
| `dealAmount`                                                                                                                                               | agreed fiat deal                             | Yes                 |
| `receivedAmount`                                                                                                                                           | LTC actually detected                        | Yes                 |
| `userMap`                                                                                                                                                  | owner/counterparty Map                       | Yes                 |
| `attempts`                                                                                                                                                 | input-retry counter                          | Yes                 |
| `date`                                                                                                                                                     | thread creation date                         | Yes                 |
| `index` (`Access_Key`)                                                                                                                                     | HD derivation index for address+key          | Yes                 |
| `addy` / `key`                                                                                                                                             | escrow address and sweep key                 | Yes                 |
| `status` (`progress`)                                                                                                                                      | human snapshot (`Money Received 12.34 USD`…) | Yes                 |
| `currency`, `current_rate`, `usd`, `ltc_to_receive`, `fee`, `sendMoreCounter`, message handles (`this.msg`, `this.bb`, `this.Newmsg`, `this.roleEmbed`, …) | live-only runtime                            | No (rebuilt per run) |

`constructor → loadState()` restores the persisted subset **if both IDs match** (that's the restart-safety contract for threads the bot died during). Every mutation of a persisted value calls `saveState()`, and writes to `trades.json` go through a save queue + `async-mutex` (see [Persistence layer](#persistence-layer)).

Statuses (`progress`) the users can observe come verbatim from the code:

```
Generated Thread Key → Started Trade With … → Money Received {usd} {currency} → Genearted Ltc_key … → Releasesd Funds at {address}
```

(Yes — those strings are as they appear in the source, typos included.)

### What a "Card" is

````
const UI = require('./ui');

await thread.send(UI.card(UI.COLORS.success)
    .text(`||<@${this.sender}>||`)                       // reference ping node (opt-in pings)
    .title('Payment Invoice', E.elite_LTC)               // `# Payment Invoice 💸`
    .divider()                                           // visible separator
    .text('- copy & paste the EXACT AMOUNT')             // plain text node
    .field(`${E.elite_terms}  Address`, `\`${addy}\``)   // **Label:** value
    .fields(['LTC', '…'], [currency, '…'])               // several **Label:** value lines in one node
    .quote('fine print here')                            // >>> blockquote
    .code('LTUX…')                                       // ``` fence ```
    .bullets(['a', 'b', 'c'])                            // • list in one node
    .heading('Next steps', { level: 2 })                 // ## …
    .gap()                                               // invisible separator
    .section(['text', '…'], { thumb: url })              // text ⟷ thumbnail section
    .row(actionRow)                                      // 1 ActionRow inside the card
    .gallery([{ url, description, spoiler }])            // media gallery
    .file('name.png')                                    // attachment:// block
    .foot('footer', { ts: unixSeconds })                 // `-# footer • <t:ts:R>`
    .spoiler()                                           // whole-card blur until click
    .msg({ ephemeral: true, files: [attachment] }));     // → send payload
````

### `Card` API

| Method                                       | Emits                    | Notes                                                |
|----------------------------------------------|--------------------------|------------------------------------------------------|
| `.title(text, emoji?)`                       | TextDisplay `# …`        | H1 heading                                           |
| `.heading(text, { emoji?, level? })`         | TextDisplay `##`/`### …` | H2/H3                                                |
| `.text(content)`                             | TextDisplay              | raw markdown inside container                        |
| `.field(label, value)`                       | TextDisplay              | `**Label:** value`                                   |
| `.fields(...pairs)`                          | TextDisplay              | compact multi-field block                            |
| `.quote(content)`                            | TextDisplay              | `>>> …`                                              |
| `.bullets(items)`                            | TextDisplay              | `• …` lines                                          |
| `.code(content)`                             | TextDisplay              | fenced block                                         |
| `.foot(text, { ts })`                        | TextDisplay `-# …`       | `-# footer • <t:ts:R>`                               |
| `.divider({ spacing?, visible? })`           | Separator                | `SeparatorSpacingSize` small/medium/large            |
| `.gap(size?)`                                | Separator                | invisible spacing                                    |
| `.section(texts, { thumb?, spoilerThumb? })` | Section + Thumbnail      | 1–3 text nodes + image                               |
| `.row(...items)`                             | ActionRow                | builders or a ready row                              |
| `.gallery(items)`                            | MediaGallery             | string URLs or `{ url, description?, spoiler? }`     |
| `.file(name, { spoiler? })`                  | File                     | needs matching **`files:`** attachment on `msg()`    |
| `.spoiler(true?)`                            | container flag           | blur entire card                                     |
| `.build()`                                   | ContainerBuilder         | raw builder (palette-style multi-container messages) |
| `.msg(opts)`                                 | **send/edit payload**    | see below                                            |

### `msg()` payload rules

```
.msg({                // defaults shown
  ephemeral: false,   // adds MessageFlags.Ephemeral alongside CV2
  files: undefined,   // attachments (required by .file / attachment:// galleries)
  allowPing: false,   // allow real pings? (see ping policy)
  ...rest             // anything else (content: null for legacy scrubs) passes through
})
```

returns:

```
{
  components: [container],
  flags: MessageFlags.IsComponentsV2 (| MessageFlags.Ephemeral),
  allowedMentions: allowPing ? { parse: ['users', 'roles'] } : { parse: [] },
  files? …
}
```

**Ping policy** — embeds never pinged, CV2 *text displays* do, so the system defaults to `allowedMentions: { parse: [] }` for every card and enables pings only at the specific sites the original bot pinged via `content` (role welcome, deal amount prompt, mismatch sandwich, rescan, wallet trigger, Trade Canceled, release/confirm cards, updated invoice, released refund…).

**Limits are enforced-ish** — `MAX_COMPONENTS = 40`, `MAX_TEXT_CHARS = 4000` are tracked across being built and warn (console) over budget.

### `withButtonState(components, disabled)`

The heart of the live edit-trail flows. Takes `message.components` from **either** layout and returns fresh components with *every interactive button* toggled:

- **classic `[ActionRow…]` message** → rows rebuilt with `.setDisabled()`
- **CV2 `[Container…]` message** → full container rebuild preserving accent + spoiler; children mapped per type:

  - `TEXT_DISPLAY` ⇒ reload content
  - `SEPARATOR` ⇒ divider flag + spacing
  - `SECTION` ⇒ text nodes reloaded; **accessory**: thumbnail re-attached, or a *button* accessory re-created with the new disabled state
  - `MEDIA_GALLERY` ⇒ items re-attached (description/spoiler kept)
  - `FILE` ⇒ name + spoiler kept

Used by `disableButtons()` / `enableButtons()` (both duplicated helper pairs in trade.js — one `async` arrow, one method — retained as-is) for start panels, role rails, wallet cards, release/cancel confirms, rescan strip and text buttons.

> **CV2 rule of thumb baked into this repo:** a CV2 message can never be edited with `content`, and `components: []` is a hard API error. When a card loses its buttons it is **re-sent buttonless as a new CV2 card** (see every `…Card().msg()` edit trail).

<a id="the-emoji-pipeline"></a>
## <img src="assets/readme/icons/emoji.svg" width="20" height="20" alt=""> The emoji pipeline

There is zero per-server emoji setup work: `emojis.txt` + `functions/emojis.js` + `functions/emojisSync.js`.

### `emojis.txt` formats

```
# 1) direct markup — an emoji ID that already exists somewhere
elite_LTC = <:elite_LTC:1494053153350357022>
check     = <a:green_tick:1481611281415798871>

# 2) bundled file (relative to repo root, preferred)
Money = ./assets/emojis/Money.png

# 3) remote image (CDN url, also uploads)
faq = https://cdn.discordapp.com/emojis/1494053058668396735.png
```

### How sync works (`functions/emojiSync.js` — on ready, before anything else)

1. List `GET /applications/{botid}/emojis` — build name→emoji map.
2. For each **source** in `E.pendingSources()`:

   - already uploaded with that name → **reuse** (restart-safe, no duplicates);
   - else `POST /applications/{botid}/emojis` with the data-URI of the bundled file / fetched URL (250 ms spacing).
3. `E.define(name, '<:Name:ID>')` injects the markup into the live store → every `${E.…}` in the codebase just works.

The store is a `Proxy` — `E.anything` looks up hits of `E.get(prop)`; unknown keys return `''` (with a console warning), and **the file is watched**: an edit to `emojis.txt` is picked up **live within ~1 s** — no restart needed.

Log lines to expect: `[emoji-sync] uploaded application emoji "Money" -> id …` then `[emoji-sync] done - X uploaded, Y reused, Z failed`.

<a id="persistence-layer"></a>
## <img src="assets/readme/icons/database.svg" width="20" height="20" alt=""> Persistence layer

### `trades.json` — the escrow ledger

```
{
  "<threadId>": {
    "interactionId": "…", "threadId": "…",
    "LTCaddy": "L…", "LTCkey": "…", "Access_Key": 42,
    "sender": "…", "receiver": "…", "status": "Money Received 12.34 USD",
    "dealAmount": 12.34, "TotalReceived": 0.12345678,
    "userMap": [["ownerId", "threadOwnerId"]], "attempts": 0, "date": "…"
  }
}
```

- Read-modify-write happens under an **async mutex**, and every write is queued (`saveQueue`/`processQueue`) so bursts collapse.
- On-load it's also the fastest cache for thread-scoped commands (`/key` etc. hit it directly via `getData(ID)`).
- A `Trade` restarts from state only when both `interactionId` **and** `threadId` match — restart-safety for threads that lived through a bot restart.

### MongoDB (`database/`)

`panel.js` schema — one doc per guild:

```
guildId (required) · channelId · messageId · buttonId
```

`createPanel` uses it to track the previous flagship panel (delete-then-recreate). Nothing else is stored in Mongo; users/deals live in `trades.json`. (Boot logs `✅ Connected to database.` / red `⚠️ Unable to connect to the database:` on failure.)

<a id="resilience--error-handling"></a>
## <img src="assets/readme/icons/shield.svg" width="20" height="20" alt=""> Resilience & error handling

<p align="center">
  <img src="assets/readme/retry-backoff.svg" alt="Retry and backoff: Tatum 3 attempts 5 s apart, BlockCypher 3 attempts with 2^n s backoff and token rotation, CryptoCompare 3 attempts" width="100%">
</p>

- **Retries everywhere:** Tatum ×3 (5 s), BlockCypher ×3 (2^n backoff), CryptoCompare ×3, partner-ID input ×5.
- **Key rotation:** BlockCypher pool; never the same token twice consecutively.
- **Mutexed persistence:** every state save is lock-protected + queued; `trades.json` gets a Nancy snapshot after each mutation.
- **Graceful thread-ending paths:** no-response timeouts delete the thread; terminal errors send a card telling users to use `/help` (and in some flows delete the thread).
- **Process-level safety nets:** `unhandledRejection` / `uncaughtException` / `uncaughtExceptionMonitor` / `shardError` all stack-log (no crash-by-default; failures occasionally send logs to a monitoring channel).

<a id="security-model"></a>
## <img src="assets/readme/icons/lock.svg" width="20" height="20" alt=""> Security model

- **Funds custody:** `mnemonic` never leaves config; keys are per-trade HD leaves (`index`). The escrow's key exists **in `trades.json`/`/key` output** (spoilered, ephemeral, admin-only badge).
- **Secrets:** `config.toml` + `trades.json` are git-ignored. `.gitignore` also excludes the `cv2/` reference folder.
- **Admin gate:** password modal for admin-panel actions. (`StrongPassword` is a constant — change it. Default-permission typos weaken the *slash UI* protection — see quirks.)
- **Confirmed-state disclosure:** escrow details shared inside the thread are Safe-Spoiler masked (`||…||`) and disclosure to the participants only.
- **Ephemeral-only:** `/addy`, `/key`, paste/QR responses never leave a permanent record.

<a id="known-quirks--technical-debt"></a>
## <img src="assets/readme/icons/warn.svg" width="20" height="20" alt=""> Known quirks & technical debt

Preserved *as-is* on purpose (byte-identical conversions, no unsolicited rewrites). Fix them when you consciously decide to:

01. **`PermissionFlagsBits.Admininstrator` typo** — `balance.js`, `close.js`, `key.js`, `manual.js`, `panels.js`, `send.js` (and leftover `balance1.js.old`). `PermissionFlagsBits[...]` returns `undefined`, so `setDefaultMemberPermissions(undefined)` is a no-op ⇒ those commands are **not** permission-hidden in the slash UI and there is **no runtime admin check** either (only `/uitest` has one). Consequence: thread-scoped info (`/key`, `balance`, release flows) is reachable by thread members. If that's unintended: fix the spelling **and** add runtime checks.
02. **Fee story mismatch** — the panel advertises *"0.25% of the amount of the deal + blockchain fees deducted from the deal when releasing"*; the code uses a **flat 0.000013 LTC** buffer added to the invoice (`this.fee`) and subtracts it again at sweep. Document/reconcile when you tune the fee model.
03. **Payout math `balance × 0.50 − fee`** — `sendLTC` sweeps **half** the escrow balance minus fee (the other half is change). This is the single-point where escrow amounts are halved; tune deliberately if you support >50 % release.
04. **Dead "Payment Received" card** — the big green completion card is built in `fetchTaxID` but never sent (the flow re-edits the *Transaction Detected* card instead). Keeping it as a reference const, flagged `void`.
05. **Literal `{this.usd}`** (and one `Amount Received` field duplicated) exist verbatim inside one field — came in via template-string copy-paste from the original.
06. **Duplicate helper definitions** — `disableButtons`/`enableButtons` and both `handleTimeout` overloads exist **twice** (methods as arrow-props and as class methods); the second binding wins.
07. **Hardcoded constants in `createPanel.js`** — `panel_channel_id`, `control_channel_id`, and the literal password `"StrongPassword"`.
08. **Deprecated `ephemeral: true`** — legacy files still pass `ephemeral` (14.x noise; supported but deprecated; `/uitest` uses `flags:`). Modernizing is an opportunity.
09. **`interpreter catches per-chat-input`** — `interactionCreate` re-reads `slashcommands/` on every chat input rather than using the prebuilt `client.commands` Collection (hot-editability trade-off).
10. **`combo URL raw grid`** — commands registered **globally** via `Routes.applicationCommands`, though the bot is a single-guild tool (a first-load latency/visibility trade-off).
11. **`trades.json` concentration** — secret keys + state in one JSON next to the process; a real deployment wants key-sharding/backup discipline.
12. **Status typo strings** — `Genearted Ltc_key`, `Releasesd Funds at`, `Administrator` possibilities are surfaced to users verbatim.

## <img src="assets/readme/icons/terminal.svg" width="20" height="20" alt=""> Setup & deployment

Quick version:

```
git clone https://github.com/iamirtasam/discord-auto-middleman.git && cd discord-auto-middleman
npm install                     # → discord.js ^14.28.0 (first 14.x with full CV2)
cp config.example.toml config.toml   # then fill every field
node index.js                   # (or: npm start)
```

The detailed walkthrough follows. Every step ends with a **Verify** line, so you know it worked before moving on.

### Step 1 — Prerequisites

- **Node.js 18 or newer.** The project is developed and tested on **v22**.
- **git**.
- A Discord **server (guild)** where you have permission to manage channels, roles, webhooks and integrations.
- Accounts for the external services (free tiers are enough to start): [MongoDB Atlas](https://www.mongodb.com/atlas), [Tatum](https://tatum.io), [BlockCypher](https://www.blockcypher.com/).

**Verify:** `node --version` prints `v18.x` or higher, and `git --version` prints a version.

### Step 2 — Discord application

1. Open the [Discord Developer Portal](https://discord.com/developers/applications) → **New Application**.
2. Open the **Bot** tab → **Reset Token** → copy the token. This is `token` in `config.toml`. Treat it like a password.
3. On the same tab, under **Privileged Gateway Intents**, enable:
   - **Message Content Intent** (the minimum the README has always required).
   - **Server Members Intent**. `index.js` requests the `GuildMembers` intent, which Discord classifies as privileged; with it disabled, login is rejected with a "disallowed intents" error.
4. The exact intents the bot requests (see the [Overview](#overview) table) are `Guilds`, `GuildMembers`, `GuildMessages`, `GuildMessageReactions` and `MessageContent`, plus the relevant `Partials`.
5. Invite the bot with the scopes `bot` and `applications.commands` (slash commands are registered **globally**). The permissions below are derived from what the bot is described as doing in this README; trim them after testing: create private threads, manage threads (rename, lock, delete), send messages in threads, manage roles (for `client_role`), and manage messages.
6. In **Server Settings → Roles**, drag the bot's role **above** the role you will use as `client_role`, otherwise role assignment is refused by Discord.

**Verify:** the bot appears in your server's member list (offline until Step 5).

### Step 3 — Clone & install

```
git clone https://github.com/iamirtasam/discord-auto-middleman.git
cd discord-auto-middleman
npm install
```

`npm install` is **required before the first run** and only needs to be repeated when dependencies change. The UI upgrade bumped `discord.js` from 14.15.3 to **^14.28.0** (the first 14.x with full Components V2 support), and the lockfile update happens automatically on install.

**Verify:** `npm ls discord.js` shows `discord.js@14.28.0` or a newer 14.x release, with no `ERR!` lines.

### Step 4 — `config.toml`

```
cp config.example.toml config.toml
```

On Windows PowerShell use `Copy-Item config.example.toml config.toml`. `config.toml` is git-ignored on purpose: never commit it.

To copy IDs from Discord, enable **User Settings → Advanced → Developer Mode**, then right-click a server, channel, role or user and choose **Copy ID**.

| Key | Example value | Where to get it | Notes |
|-----|---------------|-----------------|-------|
| `token` | `'YOUR_DISCORD_BOT_TOKEN'` | Developer Portal → your app → **Bot** → **Reset Token** | Secret. Resetting invalidates the old token. |
| `guildID` | `'YOUR_GUILD_ID'` | Right-click your server → **Copy Server ID** | Home guild, used for role assignment. |
| `thread_channel` | `'YOUR_THREAD_CHANNEL_ID'` | Right-click the channel trade threads should live in → **Copy Channel ID** | Private trade threads are created inside this channel. |
| `mongoURL` | `'YOUR_MONGODB_CONNECTION_STRING'` | MongoDB Atlas → your cluster → **Connect** → **Drivers** → copy the connection string and fill in your database user's password | Atlas also needs your server's IP on its network access list. Only the panel registry is stored here. |
| `payment_webhook` | `'YOUR_PAYMENT_LOG_WEBHOOK_URL'` | Server Settings → **Integrations** → **Webhooks** → **New Webhook** → pick the log channel → **Copy Webhook URL** | Receives the "Trade Completed" cards. |
| `transcript_webhook` | `'YOUR_TRANSCRIPT_WEBHOOK_URL'` | Same place, a second webhook (a staff-only channel is a good choice) | Receives the HTML transcript cards. |
| `support_webhook` | `'YOUR_SUPPORT_WEBHOOK_URL'` | Same place, a third webhook | Receives `/support` submissions. |
| `admin` | `["ADMIN_USER_ID_1", "ADMIN_USER_ID_2"]` | Right-click each admin user → **Copy User ID** | TOML array of strings. |
| `apikey` | `'YOUR_TATUM_API_KEY'` | [tatum.io](https://tatum.io) dashboard → API keys | Use a key for the network you intend to run on. |
| `xpub` | `'YOUR_TATUM_XPUB'` | The extended public key of the Tatum LTC wallet you generate | Every trade address is derived from this at a per-trade index. |
| `mnemonic` | `'YOUR_12_WORD_MNEMONIC'` | The mnemonic of the **same** LTC wallet as `xpub` | Secret. Keys for each trade index are derived from it, so `xpub` and `mnemonic` must belong together. Keep an offline backup. |
| `apiToken` | `['YOUR_BLOCKCYPHER_TOKEN_1', '', '', '', '']` | [blockcypher.com](https://www.blockcypher.com/) → sign up → dashboard → API tokens | Pool of up to five tokens, rotated randomly, never the same one twice in a row. Add as many as you have; see the note below. |
| `timeout` | `'60000'` | Set by you | String, milliseconds. Base confirmation-poll interval (60 seconds in the example), plus 1.5–2.5 s jitter. |
| `timeout2` | `'20000'` | Set by you | String, milliseconds. Secondary poll interval (20 seconds in the example). |
| `client_role` | `'YOUR_CLIENT_ROLE_ID'` | Right-click the role (Developer Mode) → **Copy Role ID** | Optional. Given to both parties after a completed deal. |
| `proxy` | `'user:pass@host:port'` | Your proxy provider | Optional. Currently **defined but not wired**: the per-call proxying lines are commented out in `trade.js`. |

> **Note on the BlockCypher pool.** `config.example.toml` ships one filled slot and four empty strings. The README documents the pool as random rotation over `config.apiToken[]`; to be safe, put real tokens in as many slots as you have, and remove empty slots you do not use so an empty token can never be picked.

> **Secrets.** `mnemonic`, `token` and the webhook URLs let anyone who sees them act as you. Do not paste `config.toml` into issues, screenshots or chats.

**Verify:** the file parses as TOML. A quick check from the repo root: `node -e "require('toml').parse(require('fs').readFileSync('config.toml','utf8')); console.log('config ok')"` prints `config ok`.

### Step 5 — Run

```
node index.js
```

(or `npm start`). Expected startup log lines:

```
✅ Connected to database.

[emoji-sync] done - X uploaded, Y reused, Z failed
```

**Verify:** you see all of the lines above, the bot turns **Do Not Disturb** with the activity `Watching irtasam`, and `combined.log` is created in the project folder.

### Step 6 — First-run checks

1. **Before `/panels`:** `createPanel.js` contains hard-coded constants `panel_channel_id` and `control_channel_id`, plus the admin-control password `StrongPassword` (see [Known quirks](#known-quirks--technical-debt) item 7). The panel and admin card are posted using those IDs, so set them for **your** server and change the password before going live. Changing code constants is a deliberate decision, not part of the docs workflow.
2. Run **`/panels`** in your server. *You should see:* the flagship **Start Auto Middleman** panel and a **Status card** in the panel channel, and the **Admin Controls** card in the control channel.
3. Run **`/emojicheck`**. *You should see:* every emoji key from `emojis.txt` rendered in up to three text chunks. Run it only after the `[emoji-sync] done - …` log line has appeared. Empty gaps mean an emoji key did not resolve.
4. Run **`/uitest`** (Administrator only). *You should see:* four ephemeral showcase messages: a **typography tour** (H1/H2/H3, fields, bullets, quote, code, dividers, section with thumbnail), **media** (gallery and an inline attachment file), a **palette** of the five accent colours in one message, and the **button-state harness** where *Disable All* / *Enable All* grey out and restore the button strip.
5. Click **Start Auto Middleman**. *You should see:* a **private thread** created inside your `thread_channel`, containing the card **Are you sure you want to open a trade?** with `openTrade` / `cancelTrade` buttons.

### Step 7 — Troubleshooting

| Symptom | Likely cause | What to do |
|---------|--------------|------------|
| Bot stays offline; log shows "disallowed intents" or a login error | Privileged intents not enabled, or a wrong/reset `token` | Enable **Message Content Intent** and **Server Members Intent** (Step 2), re-check `token`, restart. |
| Slash commands do not appear | Commands are registered **globally** on startup; the invite may lack `applications.commands` | Re-invite with both scopes and wait for Discord to propagate global commands. |
| Emojis render as empty strings | `/emojicheck` or UI used before sync finished, or a bad source in `emojis.txt` | Wait for `[emoji-sync] done - …`, then re-run. Unknown keys return `''` with a console warning; check the source formats in [The emoji pipeline](#the-emoji-pipeline). |
| Panels duplicated or old panel still shown | Stale panel document in MongoDB, or an old panel message removed by hand | Run `/panels` again: it deletes the old message, drops the doc and re-creates everything. |
| Boot shows `⚠️ Unable to connect to the database:` | Wrong `mongoURL`, wrong password, or IP not allowed in Atlas | Fix the connection string / network access list. |
| Deposits are not detected | BlockCypher token pool exhausted, invalid or containing empty slots; wrong network key | Add more real tokens, remove empty slots, check `combined.log` for BlockCypher errors. See [Resilience](#resilience--error-handling). |
| Address/key generation fails and the thread points users to `/help` | Tatum `apikey`, `xpub` or `mnemonic` wrong, or Tatum unreachable | Verify the Tatum values; each call retries 3× with 5 s spacing before failing. |
| Admin commands usable by non-admins; `/key` visible to thread members | The `Admininstrator` typo means no permission hiding and no runtime check | See [Known quirks](#known-quirks--technical-debt) item 1. Fixing it is a deliberate code change. |
| Panel or admin card shows up in the wrong channel | Hard-coded `panel_channel_id` / `control_channel_id` in `createPanel.js` | See Step 6 and quirk 7. |
| No `client_role` after a deal | `client_role` empty, or the bot role sits below it | Set the role ID and move the bot's role above it. |

## <img src="assets/readme/icons/branch.svg" width="20" height="20" alt=""> Making changes

Developer workflow for working on the bot itself. Contributors should also read [CONTRIBUTING.md](CONTRIBUTING.md).

### Project rules that actually exist

- **All UI flows through `functions/ui.js`.** Build messages with `Card` (see [The Components V2 UI design system](#the-components-v2-ui-design-system)); do not hand-roll components or add `EmbedBuilder`.
- **Every `customId` must either appear in the [Button & interaction registry](#button--interaction-registry) or carry its own prefix for isolation** (for example `uitest_*`, which `interactionCreate` ignores silently).
- **CV2 hard rules:** no `content` beside a CV2 payload, and no empty `components: []`. When a card loses its buttons, send a buttonless card instead.
- **Pings are opt-in.** Cards default to `allowedMentions: { parse: [] }`; enable real pings only with `allowPing: true` at the specific sites that need them.

### Verification before any commit

1. Syntax-check **every touched file**, and keep the whole repo green:

   ```
   node --check path/to/file.js
   ```

   Whole repo, bash: `git ls-files '*.js' | xargs -n1 node --check`. PowerShell: `git ls-files "*.js" | ForEach-Object { node --check $_ }`.
2. For visual changes, run **`/uitest`** and look at the result (see [`/uitest`](#uitest--the-cv2-visual-lab)).

### Commit message conventions

Small, grep-able conventional commits: `type(scope): imperative summary`. Prefixes and scopes in use:

| Pattern | Used for | Example |
|---------|----------|---------|
| `feat(ui): …` | new design-system capability | `feat(ui): add …` |
| `feat(emoji-sync): …` | emoji pipeline features | `feat(emoji-sync): …` |
| `fix(uitest): …` | fixes inside the visual lab | `fix(uitest): …` |
| `cv2(trade3): …` | one cluster of the CV2 conversion of a file | `cv2(trade3): …` |
| `process/readme: …` | documentation and process | `process/readme: …` |

Keep one conversion scope per commit, write the summary in the imperative, and finish every commit with the syntax check above.

### Do-not-touch list

- **`config.toml`**: secrets, git-ignored, never committed.
- **`trades.json`**: live escrow state including private keys, git-ignored, never committed.
- **`cv2/`**: local Components V2 reference notes, git-ignored, **do not commit**.
- **`node_modules/`**: never committed.
- **Protected quirks** listed in [Known quirks & technical debt](#known-quirks--technical-debt). They are preserved on purpose; changing one is a deliberate decision, never incidental hygiene.

### Documenting new flows

Add the new stage or branch to the diagrams in [How an escrow trade works](#how-an-escrow-trade-works) rather than inventing a new format. Diagram conventions used in `assets/readme/`: a deep-neutral `#101613` panel, text `#e6ffe9`, strokes in the `#1ec42c` / `#00b300` green family, danger red `#ED4245` only for cancel/error branches, a monospace font stack, `role="img"` plus `<title>` and `<desc>`, and no external fonts, logos or scripts.
